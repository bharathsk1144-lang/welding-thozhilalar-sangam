# November 7 client testing link: staging preparation

Historical checklist for the earlier Vercel/paid-disk plan. The current free-tier deployment uses Cloudflare Pages, Render Free, and authenticated Cloudinary storage; do not use the upload-mount steps below. Follow [private cloud storage and recovery gates](private-cloud-storage-runbook.md).

This repository is prepared for a Vercel frontend and a separate ASP.NET Core API. No account, service, database, DNS record, deployment, or client link has been created by this preparation. Use synthetic member details and synthetic image files only.

## Repository settings ready for staging

- Vercel project root: `client`; install `npm ci`; build `npm run build`; output `dist`. `client/vercel.json` rewrites React routes to the SPA entry point. The browser must fetch the API and protected `/uploads` from the separate HTTPS API origin.
- Set Vercel Preview `VITE_API_BASE_URL=https://<staging-api-host>/api` before building. This value is public browser configuration. The old same-origin `/api` example does not fit this architecture. Redeploy the preview after changing it.
- Build the backend from the repository root with `Dockerfile` and `.dockerignore`; expose port 8080. The runtime image omits local `appsettings.json` defaults. All staging settings are supplied by the host, using `deploy/backend.env.example` as a template. Do not upload a filled env file to the repository.
- Use `Authentication__OtpEnabled=false` for November 8 registration testing. The registration page reads the backend setting. The backend still validates registration and prevents duplicate mobiles; new accounts store `MobileVerified=false`. Password login remains available. Forgot-password OTP remains required and unverified mobiles cannot recover by OTP.
- Host health check: `/health/ready` (database ping; returns 503 if unavailable). `/health/live` checks only process liveness. Configure HTTPS at the host proxy and exact Vercel Preview origin in `Cors__AllowedOrigins__0`.
- The API rate limits registration and other auth requests to 20 requests per minute per client IP. If behind a proxy, configure only its actual IP in `ReverseProxy__KnownProxies__0` after verifying the host's forwarding behavior.

## Exact steps to obtain a working client link

1. Create owner-controlled Vercel and .NET host accounts. Choose a backend plan with an actual persistent private disk; an ephemeral filesystem cannot retain uploads. Confirm terms, cost, support owner, and an HTTPS API hostname. Render paid web service with a persistent disk is one possible host, not an account already configured here.
2. Create a separate MongoDB Atlas staging project/cluster and database named `WTS_Staging`. Create an application database user scoped to staging and allow only the backend host's outbound IP/network. Do not copy the local development database or member documents. Confirm TLS connectivity from the host.
3. Create an empty, private durable upload mount at `/var/lib/wts/uploads`, writable by the container's non-root `app` user. Set `Uploads__RootPath` to that mount. Verify the mounted path survives a host restart and is never web-served directly. Use synthetic image uploads only until access control, encryption, retention, backup, and restore are verified.
4. Generate a unique staging admin password and Identity V3 hash offline with `dotnet run --project tools/AdminSecret/AdminSecret.csproj --configuration Release`. In host secret settings, set the hash as `Admin__PasswordHash`, a different random `Admin__JwtKey` of at least 32 bytes, an operator username, the HTTPS API issuer, and the Vercel Preview audience. Leave `Admin__Password` empty. Never put these in `VITE_` settings or commit a filled env file.
5. Configure remaining backend environment settings from `deploy/backend.env.example`: authenticated Atlas URI, `WTS_Staging`, `Authentication__OtpEnabled=false`, the private upload mount, and `SMS_ENABLED=false` until a reviewed provider exists. Do not invent an association registration number or President home address. Build and start the backend on the separate host; require HTTPS `/health/live` and `/health/ready` to return 200. First startup may create required indexes and seed districts in this new staging database only.
6. Create the Vercel project with root directory `client`, Preview environment `VITE_API_BASE_URL=https://<staging-api-host>/api`, and the approved public branding values in `deploy/frontend.env.example`. Obtain its generated Preview URL. Put that exact HTTPS origin in backend `Cors__AllowedOrigins__0`, then restart/redeploy the staging backend and test a browser CORS preflight. A generated preview URL may change on a new deployment; update the allowlist when it does.
7. From the Vercel Preview URL, use synthetic data to test registration without OTP, duplicate mobile rejection, password member login, admin login/dashboard, district management, protected image access, card preview, PDF/PNG export, mobile layout, and recovery denial for an unverified mobile. Test direct refresh of `/register`, `/user-login`, and `/admin/dashboard`. Review the seeded district WhatsApp links, which are placeholders, and configure approved links before asking anyone to join. Confirm local development data and uploads are absent from the staging database and disk.
8. Create a consistent staging database backup and upload-volume snapshot, store both privately, and restore to a new isolated namespace and directory. Verify document counts, references, and file hashes. Record who owns the restore process and the retention schedule. Share the Preview URL with the client only after these checks pass.

## Remaining launch gates

- No staging host, Vercel project, Atlas project, admin secret, HTTPS URL, private durable mount, or verified backup currently exists in this workspace. Docker is not installed locally, so the image has not been built or run here.
- The configured SMS sender does not deliver production OTP. Forgot-password recovery therefore remains unavailable until an approved provider and controlled delivery test exist, even for previously verified mobiles.
- Unverified mobiles have no self-service ownership-verification flow yet. Their password login works; OTP password recovery remains blocked until a separately verified process sets `MobileVerified=true`.
- Seeded district WhatsApp links are placeholders. Approved real links and a privacy-safe test group are still required for full end-to-end client registration testing.
- The isolated release targets .NET 10 and MongoDB Driver 3.13; the transitive SharpCompress version is 0.48.1. The synthetic backend checks passed after the upgrade. Live Cloudinary privacy and isolated restore are still required before a production launch.
- Official-domain DNS changes, real Aadhaar uploads, production data copy, deployment, and client access remain outside this preparation.
